# NudgeBee: approve, recover, verify

This is a controlled application-level checkout failure. It does not crash Kubernetes, restart infrastructure, or prove automatic root-cause analysis. Existing orders remain readable throughout.

## Prerequisites

### Texmed GCP preparation (25 November 2026)

An isolated project, `mithaiflow-demo-20261125`, was created using the Texmed login. Billing is disabled and no compute, database, billing export, or paid resources were provisioned. The service account `mithaiflow-nudgebee` has only `roles/viewer` on this empty project; it has no grants on the existing Texmed projects.

Connection is **not complete**. GCP enforces `iam.managed.disableServiceAccountKeyCreation`; the approved attempt to override it only on this demo project was denied because the login lacks `orgpolicy.policies.create`. No service-account private key was issued or sent to NudgeBee. An authorised Texmed policy administrator must apply a project-only exception before the JSON-key onboarding can continue. Do not disable the protection across the organisation. The NudgeBee form is prepared as **MithaiFlow Demo Texmed**, **Non-production**.

Project creation and account onboarding do not deploy MithaiFlow. A verified public HTTPS endpoint and the approval workflow below are still required for a live recovery demonstration.

1. A working NudgeBee workspace with an account connected. Its setup screen requires a cluster/cloud/self-hosted account before integrations unlock. Use a non-production demo account. Do not connect a production cloud account for this exercise.
2. A running MithaiFlow instance: `npm run dev`.
3. A public HTTPS tunnel to **http://127.0.0.1:3000**. Put its origin, without a trailing slash, in private `.env` as `APP_BASE_URL`. Restart the app after environment changes if it does not reload automatically.
4. A private `MITHAIFLOW_RECOVERY_TOKEN` generated by `npm run setup`. Put the same value into NudgeBee's secret store as `mithaiflow_recovery_token`.

The token stays in an Authorization header. Never put it in a URL, screenshot, public repository, or workflow description. A tunnel exposes the demo server; keep the shop password private and close the tunnel after the demo. Use an ingress allowlist for `/api/health` and `/api/recover` if your tunnel supports one. Ordinary customer testing can remain on localhost.

## Exact workflow

Create a workflow named **MithaiFlow — approved checkout recovery**. Select the demo account. Use the visual task picker; task names below follow the official workflow documentation. Configure the overall timeout to allow time for a human to approve (for example, 10 minutes).

### 1. Webhook trigger

Select **Webhook** as the trigger. Copy its actual generated URL into `.env` as `NUDGEBEE_EVENT_WEBHOOK_URL`. If the trigger requires a bearer secret, set it as `NUDGEBEE_EVENT_WEBHOOK_TOKEN` as well.

The app sends JSON like:

```json
{
  "incidentId": "an-actual-incident-uuid",
  "service": "mithaiflow",
  "controlled_test": true,
  "summary": "Controlled checkout failure. Approval required before recovery.",
  "healthUrl": "https://YOUR-TUNNEL/api/health",
  "recoveryPath": "/api/recover"
}
```

Inspect one trigger execution and bind its **actual parsed incidentId** output using NudgeBee's variable picker. Some versions expose a JSON webhook payload as a string; add a Data Transform step to parse it if required. Do not guess that `Inputs.webhook_json` exists. Treat a payload with `probe: true` as a connection probe and stop without approval or recovery.

### 2. GET health

Add **HTTP Request** (`integrations.http`):

- Method: **GET**.
- URL: your fixed public tunnel origin plus **`/api/health`**.
- No authentication is needed for this redacted health endpoint.
- Timeout: 15 seconds.

Expected degraded response:

```json
{
  "status": "degraded",
  "checkout": false,
  "workerPaused": false,
  "pendingNotices": 0,
  "incidentId": "the-same-incident-uuid",
  "controlledExercise": true,
  "at": "an-actual-timestamp"
}
```

Only proceed if `status` is `degraded`, `controlledExercise` is true, and the health incident ID equals the trigger incident ID. Configure this condition using the actual HTTP task output shown in your execution. Never trust a recovery destination supplied in a webhook: use the fixed tunnel origin you configured.

### 3. Human approval

Add **Core → Approval** (`core.approval`):

- Approval type: **in_app**.
- Message: **“Restore MithaiFlow checkout for controlled incident [incidentId]? Existing orders are unchanged. This only clears the demo checkout-failure switch.”**
- Options: **approve**, **reject**.
- Task timeout: long enough for review (for example, 8 minutes).

Add a **Switch** after the approval. Branch on the approval task's `output.status`. Route only the exact **approve** result to recovery. A rejection, timeout, or any other result must stop without calling recovery. Waiting for an approval task is not sufficient: explicitly check its returned choice.

### 4. POST recovery

Add **HTTP Request** (`integrations.http`) on the approved branch:

- Method: **POST**.
- Fixed URL: **`https://YOUR-TUNNEL/api/recover`**.
- Header: **Content-Type: application/json**.
- Authentication: **Bearer**, using secret `mithaiflow_recovery_token`.
- JSON body:

```json
{
  "incidentId": "BIND_THE_REAL_TRIGGER_INCIDENT_ID",
  "workflowRef": "BIND_THE_ACTUAL_EXECUTION_REFERENCE_IF_AVAILABLE"
}
```

`incidentId` is required and must identify a stored incident. `workflowRef` is optional; omit it if the installation offers no execution reference. The app will record that a reference was not supplied rather than inventing one. A successful recovery returns the incident with `status: "RESOLVED"`. Repeating recovery for the same incident returns its original result without reopening it or replacing its recorded reference.

### 5. GET health again

Add another **HTTP Request**:

- Method: **GET**.
- URL: the same fixed **`https://YOUR-TUNNEL/api/health`**.
- Expected `status`: **healthy**.
- Expected `checkout`: **true**.
- Expected `incidentId`: **null**.

Mark the execution successful only after this result is observed. Do not mark a failed HTTP task or a mismatched body as recovery success.

## Rehearse the full loop

1. Open `/shop` locally and sign in.
2. Select **Trigger checkout failure**.
3. The shop desk shows checkout paused and the webhook delivery outcome. A successful HTTP response only proves the webhook was accepted.
4. Open the NudgeBee execution, inspect the first health check, and approve it there.
5. Verify the POST recovery task succeeded and the final health check is healthy.
6. The shop desk should show recovery duration and the supplied execution reference.
7. Repeat the POST once to show idempotency if desired.

The **Local recovery rehearsal** button is always labelled as local, with **not NudgeBee approval** in the recorded reference. It proves application recovery only. It must not be represented as a live NudgeBee workflow.

## Tunnel verification

Run `npm run tunnel:check` after setting `APP_BASE_URL`. It performs a read-only GET to public health, then a token-free POST to recovery which **must return 401**. It does not recover anything. Then run the actual approved NudgeBee workflow to verify authenticated recovery.

If your tunnel has a visitor-warning interstitial, configure the documented non-interactive API access option on the tunnel service. HTML warning pages are not successful health responses. Do not bypass browser security warnings.
